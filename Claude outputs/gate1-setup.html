Rule 1

Never paste a secret value into this chat. Not once, not to "confirm" it. A secret is any of these:

  • The AWS Secret Access Key (the long string, not the shorter Access Key ID)
  • The Neon connection string (it starts with postgresql:// and has a password inside it)
  • Any Vercel token

If you want to tell Claude a step is done, say "key created" or "bucket done" — never the value itself. Save real values in a password manager or an encrypted note on your own machine.

1

AWS — ask for model access

Do this first. Approval takes a few minutes in the background — start it, then do steps 2–4 while it processes.

  1. Sign in to the AWS Console. Top‑right region picker: set it to US East (N. Virginia). This is region us-east-1. Use this same region for every AWS step below.
  2. Go to the Bedrock console.
  3. Left menu path: Bedrock configurations→Model access
  4. Click Modify model access.
  5. Check the box for every model under these four provider names: Anthropic, Amazon, Meta, Mistral AI. Select all of them, not just one variant each.
i

Why "all of them," not one exact model? The project needs 5 specific models (a Claude Haiku, a Claude Sonnet, one Nova, one Llama, one Mistral) but the exact version IDs haven't been picked yet — that happens in a later step, once real prices get written down. Requesting access is free; you're only billed when a model is actually called. Checking every box now avoids a second trip back to this screen.

  1. Click Next, then Submit.
  2. Anthropic only: a "Submit use case details" form appears. This is the one provider that reviews the answer before granting access. Paste this into the description field:
# paste this exact text into Anthropic's use-case form
Benchmarking model accuracy, cost, and latency across providers
for a personal AI infrastructure research project (Giggit AI).
Non-production evaluation and research use.
  1. Submit that form. The other three providers (Amazon, Meta, Mistral AI) just need their license terms accepted — no form.
Done when
  • The Model access page shows every model as "Access granted" or "In progress" for all 4 providers. "In progress" is fine — it finishes in the background.
2

AWS — create the storage bucket

~2 min · this holds the project's raw data files, nothing secret

  1. Go to the S3 console.
  2. Path: General purpose buckets→Create bucket
  3. Bucket name — type exactly:
giggit-area-raw-payments
!

Bucket names are shared across all AWS customers worldwide, so this exact name might already be taken by someone else. If AWS says it's unavailable, add your initials and a number, e.g. giggit-area-raw-payments-la26. The name itself isn't secret — just note whichever one you end up with.

  1. Region: confirm it says US East (N. Virginia) / us-east-1.
  2. Object Ownership: leave the default, Bucket owner enforced.
  3. Block Public Access settings: leave every box checked (the default). Do not uncheck these.
  4. Bucket Versioning: leave Disable (default) — not needed here.
  5. Default encryption: leave the default (SSE‑S3).
  6. Click Create bucket.
Done when
  • The bucket exists and shows in your bucket list. Note down its exact name — you'll need it in Step 3, and again later.
3

AWS — create one narrow IAM user

~6 min · this is the credential the deployed app will use — it can only call these 5 models and touch this one bucket, nothing else

  1. Go to the IAM console.
  2. Path: Users→Create user
  3. User name: giggit-bedrock-app (just a label, not secret).
  4. Leave "Provide user access to the AWS Management Console" unchecked. This user is for code, not for logging into AWS as a person.
  5. Click Next. Under permissions options, choose Attach policies directly.
  6. Click Create policy (opens a new tab).
  7. Switch to the JSON tab in the policy editor and replace everything with this — first swap in your real bucket name from Step 2 wherever you see YOUR-BUCKET-NAME (two places):
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "BedrockInvokeGiggitModels",
      "Effect": "Allow",
      "Action": [
        "bedrock:InvokeModel",
        "bedrock:InvokeModelWithResponseStream"
      ],
      "Resource": [
        "arn:aws:bedrock:us-east-1::foundation-model/anthropic.claude-*",
        "arn:aws:bedrock:us-east-1::foundation-model/amazon.nova-*",
        "arn:aws:bedrock:us-east-1::foundation-model/meta.llama*",
        "arn:aws:bedrock:us-east-1::foundation-model/mistral.*"
      ]
    },
    {
      "Sid": "S3RawDataBucketOnly",
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:PutObject",
        "s3:ListBucket"
      ],
      "Resource": [
        "arn:aws:s3:::YOUR-BUCKET-NAME",
        "arn:aws:s3:::YOUR-BUCKET-NAME/*"
      ]
    }
  ]
}
i

Why this exact shape, for the audit trail: the policy names the 4 model providers by prefix instead of one exact model ID each, because the exact 5 model versions aren't chosen yet (Step 1's note). It's still far narrower than AWS's own default suggestion — it cannot touch any other AWS service, any other bucket, or any model outside these 4 providers. This choice is logged as decision D17 in AREA's CONTEXT.md and D22 in Model Bench's.

  1. Click Next. Name the policy giggit-bedrock-s3-policy. Click Create policy.
  2. Go back to the Create user tab. Refresh the policy list, search giggit-bedrock-s3-policy, check it.
  3. Click Next, then Create user.
  4. Click into the new user → Security credentials tab → Access keys section → Create access key.
  5. On "Access key best practices & alternatives," choose Other, then Next.
  6. (Optional) add a description tag, e.g. giggit project key. Click Create access key.
  7. Click Show to reveal the secret key, then Download .csv file.
!

AWS shows the Secret Access Key exactly once. If you don't download it now, you'll have to delete this key and make a new one. Save the .csv somewhere private — a password manager, or an encrypted note on your own machine. Not in this chat, not in email, not in either repo.

Done when
  • One IAM user exists with the policy above attached.
  • One .csv file is downloaded and saved somewhere private, containing an Access Key ID and a Secret Access Key.
4

AWS — set a spending alert

~3 min · an email tripwire, not a hard cap — AWS Budgets can't stop spending by itself, it only warns you

  1. Go to the Billing and Cost Management console.
  2. Path: Budgets→Create budget
  3. Choose Customize (advanced) → Cost budget → Next.
  4. Budget name: giggit-monthly-alert.
  5. Period: Monthly. Budget renewal type: Recurring budget.
  6. Budgeting method: Fixed. Enter your monthly amount — pick one below.
Tight
$10

Trips fast. May fire during one heavy afternoon of testing all 5 models.

Recommended
$25

Room for several days of benchmarking across models before it warns you.

Loose
$50

For a longer stretch of testing without re-checking the alert.

  1. Click Next. Click Add an alert threshold.
  2. Threshold: 80% of budget, type Actual.
  3. Email recipients: your own email address.
  4. Click Next twice (skip "budget actions"), review, click Create budget.
Done when
  • One budget exists with one email alert attached to your own address.

Vercel — confirm your login

~2 min · light touch on purpose — no project exists to connect yet

  1. Go to vercel.com and sign in (or sign up — email, GitHub, or GitLab all work).
  2. On your real Mac Terminal — not any sandbox or browsing agent — run:
vercel whoami
  • Prints your account name → you're already logged in. Nothing else to do.
  • Says you're logged out → run vercel login and follow the prompt (it opens a browser tab or emails you a link to confirm).
i

Model Bench's own notes (CONTEXT.md, decision D4) record that the Vercel CLI already lives on your real Mac and was logged in there before. This step just confirms that's still true.

!

Do not run vercel link, vercel env add, or any deploy command yet. There's no project to link to — that's built in the next task.

Done when
  • vercel whoami prints your account name in your real Terminal.
